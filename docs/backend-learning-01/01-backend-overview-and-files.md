# Урок 01: Как работает backend в этом проекте

## Цель этого урока
Понять backend как систему: от запуска сервера до ответа API, и роль каждого файла в папке `backend`.

## 1) Быстрая карта backend

Папка `backend` в этом проекте разделена так:

- `src/` — исходный код сервера
- `tests/` — автотесты на ключевую логику
- `.env`, `.env.example` — конфигурация окружения
- `package.json`, `package-lock.json` — зависимости и npm-скрипты
- `node_modules/` — установленные библиотеки (их обычно не изучаем как код проекта)

Главная причинно-следственная цепочка запроса:

1. Клиент отправляет HTTP-запрос.
2. Express в `src/app.js` направляет запрос в нужный `route`.
3. `route` валидирует вход и вызывает `service`.
4. `service` работает с БД и бизнес-логикой (`lib/*`).
5. Возвращается JSON-ответ клиенту.

## 2) Что такое `src`, `data`, `lib`

- `src` — весь runtime-код backend. Это то, что реально исполняется при `node src/index.js`.
- `src/data` — встроенные данные (seed-справочник продуктов), которые используются при первичной синхронизации каталога.
- `src/lib` — переиспользуемые утилиты и доменные helper-функции: валидация, криптография, константы, ошибки, конфиг, нормализация названий продуктов.

## 3) Разбор каждого файла `backend`

## Конфиги и зависимости https://habr.com/ru/companies/domclick/articles/513130/

### `backend/package.json`
Роль: описание backend-пакета, скриптов и зависимостей.

Зачем нужен:
- команды `npm run dev`, `npm start`, `npm test`
- фиксирует, что backend использует `express`, `pg`, `dotenv`, `cors`

Связь: без него невозможно корректно установить и запускать сервис.

### `backend/package-lock.json`
Роль: lock-файл точных версий зависимостей.

Зачем нужен:
- одинаковые версии библиотек на всех машинах
- воспроизводимые сборки и стабильное поведение

### `backend/.env.example`
Роль: шаблон необходимых переменных окружения.

Зачем нужен:
- onboarding: разработчик быстро понимает, что нужно настроить

### `backend/.env`
Роль: локальные значения переменных окружения.

Зачем нужен:
- хранит конкретные параметры запуска (порт, БД, секрет токена)

Важно: в проде значения обычно другие.

### `backend/node_modules/*`
Роль: код внешних библиотек.

Зачем нужен:
- runtime backend

Как учить: не читать целиком. Сначала учить API библиотек через документацию (`express`, `pg`).

## Точка входа и инициализация

### `backend/src/index.js`
Роль: точка входа backend.

Что делает:
- получает `app`
- подключает пул БД
- читает конфиг
- перед стартом вызывает `syncNutritionCatalog(pool)`
- запускает `app.listen`

Причина: сервер стартует только после подготовки каталога продуктов. Это снижает риск пустого каталога при первом запуске.

### `backend/src/app.js`
Роль: композиция Express-приложения.

Что делает:
- включает CORS и JSON body parser
- подключает роуты:
  - `/api/health`
  - `/api/auth`
  - `/api/catalog`
  - `/api/daily`
- отдает 404 для неизвестных маршрутов

Причина: `app.js` отделяет HTTP-слой от бизнес-логики.

### `backend/src/db.js`
Роль: создание `Pool` из `pg`.

Что делает:
- берет настройки из `config`
- экспортирует единый пул подключений

Причина: один пул на процесс = эффективная работа с PostgreSQL.

## `src/lib` (утилиты и ядро доменных правил)

### `backend/src/lib/config.js`
Роль: централизованное чтение и валидация ENV.

Что делает:
- загружает `.env`
- валидирует числовые переменные
- отдает объект `getConfig()`

Причина: чтобы не разбрасывать `process.env` по коду и ловить ошибки конфигурации раньше.

### `backend/src/lib/constants.js`
Роль: доменные константы питания.

Содержит:
- ключи секций (`breakfast`, `lunch`...)
- русские подписи секций
- целевые нормы по умолчанию

Причина: единый источник истины для секций и целей.

### `backend/src/lib/crypto.js`
Роль: безопасность паролей и токенов.

Что делает:
- `createPasswordSalt`
- `hashPassword` через PBKDF2
- `createToken` и `verifyToken` (подписанный токен)

Причина: auth-логика должна быть изолирована и тестируема.

### `backend/src/lib/errors.js`
Роль: единый формат прикладных ошибок (`statusCode`).

Причина: сервисы могут бросать понятные ошибки, а роуты корректно мапят их в HTTP-ответ.

### `backend/src/lib/validation.js`
Роль: валидация входящих данных API.

Что делает:
- проверка дат
- проверка payload для auth/login/profile
- проверка дневника питания и health metrics
- проверка custom-продукта

Причина: валидировать как можно ближе ко входу, чтобы сервисы работали с корректными данными.

### `backend/src/lib/product-catalog.js`
Роль: правила каталога продуктов.

Что делает:
- нормализация имени продукта (`normalizeProductName`)
- выбор типа продукта и разрешенных секций по `section_key`

Причина: единообразие поиска/дедупликации и доменные ограничения (например, вода -> только `water`).

## `src/middleware`

### `backend/src/middleware/auth.middleware.js`
Роль: защита приватных маршрутов.

Что делает:
- достает Bearer token
- валидирует подпись токена
- кладет `request.user`

Причина: все защищенные маршруты переиспользуют один middleware вместо дублирования.

## `src/routes` (HTTP слой)

### `backend/src/routes/health.routes.js`
Роль: health-check endpoint.

Причина: быстро понять, что сервис жив.

### `backend/src/routes/auth.routes.js`
Роль: API авторизации и профиля.

Endpoints:
- `POST /register`
- `POST /login`
- `GET /me`
- `PUT /me`

Причина: роуты управляют HTTP-частью (коды, сообщения, middleware), а детали делает `auth.service`.

### `backend/src/routes/catalog.routes.js`
Роль: API каталога продуктов.

Endpoints:
- `GET /` (получить каталог)
- `POST /custom` (добавить свой продукт)

Причина: разделение "каталог" как отдельного bounded context.

### `backend/src/routes/daily.routes.js`
Роль: API дневника питания по дате.

Endpoints:
- `GET /:date`
- `PUT /:date`

Причина: дневник — отдельный сценарий, где много валидации и транзакционных операций.

## `src/services` (бизнес-логика)

### `backend/src/services/auth.service.js`
Роль: регистрация, логин, чтение/обновление профиля.

Что важно:
- нормализация user row (числа из БД -> Number)
- генерация токена
- хеширование пароля

Причина: бизнес-правила auth нельзя держать в route.

### `backend/src/services/catalog.service.js`
Роль: синхронизация seed-каталога и custom-продукты пользователя.

Что важно:
- `syncNutritionCatalog`: миграция схемы + upsert seed
- уникальность продуктов по нормализованному имени и владельцу
- ручные seed-записи для воды

Причина: каталог должен быть инициализирован и защищен от дублей.

### `backend/src/services/daily.service.js`
Роль: сценарий чтения/сохранения дневника за день.

Что важно:
- собирает payload из нескольких таблиц
- валидирует, что product разрешен для section
- сохраняет в транзакции: запись дня, entries, health metrics
- возвращает уже пересчитанный dashboard

Причина: один use-case = один сервисный модуль.

### `backend/src/services/nutrition.service.js`
Роль: чистая математика по питанию.

Что делает:
- расчет нутриентов по порции
- summary/targets/balances/progress
- группировка entries по секциям

Причина: чистые функции легко тестировать отдельно от БД.

## `src/data`

### `backend/src/data/nutrition-products.json`
Роль: большой seed-справочник продуктов (10k+ строк).

Причина: иметь стартовую базу питания без ручного ввода пользователем.

Как учить: не читать весь файл. Важно понять формат одной записи и как файл используется в `catalog.service.js`.

## Тесты

### `backend/tests/auth.test.js`
Проверяет: крипто-функции и часть валидации auth/profile/health.

### `backend/tests/nutrition.service.test.js`
Проверяет: расчеты нутриентов, summary, dashboard.

### `backend/tests/product-catalog.test.js`
Проверяет: нормализацию названия и конфиг секций.

### `backend/tests/validation.test.js`
Проверяет: валидации даты, дневника, custom-продукта.

Причина тестов: фиксируют поведение и страхуют от регрессий при рефакторинге.

## 4) Главные связи (очень важно)

1. `index.js` -> `app.js` + `db.js` + `catalog.service.js`.
2. `app.js` -> `routes/*`.
3. `routes/*` -> `validation.js` + `middleware/auth` + `services/*`.
4. `services/*` -> `db` (через `pool`) + `lib/*`.
5. `daily.service` -> `nutrition.service` (чистые расчеты).

Это и есть основной "скелет" backend в production-проектах.

## 5) Как выучить это на практике

План обучения на 5 шагов:

1. Пройти путь одного запроса вручную.
   Пример: `PUT /api/daily/:date` и последовательно открыть `daily.routes.js -> validation.js -> daily.service.js -> nutrition.service.js`.

2. Выписать контракты данных.
   Для каждого endpoint записать входной payload, выходной payload, ошибки.

3. Потренировать рефакторинг без изменения поведения.
   Например, вынести маленький helper из `daily.service.js` и прогнать тесты.

4. Написать 2-3 новых теста.
   Например, кейс с недопустимой секцией для продукта и кейс с пустыми записями.

5. Пересобрать мини-версию сервиса с нуля.
   Только `health + auth + one daily route`. Это лучший способ закрепить архитектуру.

## 6) Что спросить себя для собеседования

- Почему валидация находится в routes, а не в services?
- Почему для `saveDailyPayload` нужна транзакция?
- Чем чистые функции (`nutrition.service`) лучше смешанных (БД + математика в одном месте)?
- Какие риски у самописного токена и чем JWT отличается?
- Где здесь может быть bottleneck при росте данных?

Если хочешь, следующим шагом сделаем "Урок 02" в том же формате: разберем 1 endpoint до SQL-уровня и нарисуем sequence-flow по строкам кода.

## 7) Самопроверка (10 вопросов + ответы)

1. Вопрос: Зачем нужен `src/index.js`, если есть `src/app.js`?
   Ответ: `app.js` собирает Express-приложение, а `index.js` запускает процесс: подготавливает данные (`syncNutritionCatalog`) и вызывает `listen`.

2. Вопрос: Где лучше делать первичную валидацию входных данных и почему?
   Ответ: В routes (или middleware рядом с routes), чтобы не пускать невалидные данные глубже в services и БД.

3. Вопрос: Почему `saveDailyPayload` использует транзакцию?
   Ответ: Потому что там несколько связанных операций (daily record, entries, health metrics). Нужно сохранить все вместе или не сохранить ничего.

4. Вопрос: Зачем нужен отдельный `nutrition.service.js`?
   Ответ: Он изолирует чистые расчеты от БД и HTTP, поэтому код проще тестировать, переиспользовать и менять.

5. Вопрос: Что хранит `src/data/nutrition-products.json` и зачем он вообще в проекте?
   Ответ: Seed-каталог продуктов с нутриентами. Нужен для стартового наполнения БД, чтобы пользователь сразу работал с готовым справочником.

6. Вопрос: Какую роль выполняет `auth.middleware.js`?
   Ответ: Проверяет Bearer token, извлекает пользователя и либо пропускает запрос дальше, либо возвращает `401`.

7. Вопрос: Для чего нормализовать название продукта (`normalizeProductName`)?
   Ответ: Чтобы корректно искать дубли и сравнивать названия в едином виде (регистр, символы, `ё/е`).

8. Вопрос: Почему в проекте есть и `.env.example`, и `.env`?
   Ответ: `.env.example` показывает обязательные переменные для запуска, `.env` хранит локальные значения конкретной среды.

9. Вопрос: Что проверяют тесты в `backend/tests/` на уровне идеи?
   Ответ: Критичные правила системы: валидация входа, математика нутриентов, нормализация каталога, крипто- и auth-поведение.

10. Вопрос: Как выглядит базовая цепочка обработки запроса в этом backend?
    Ответ: `client -> app.js -> route -> validation -> service -> db/lib -> response`.
